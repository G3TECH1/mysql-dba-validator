# Local connector

The local connector lets the MySQL DBA Validator page work with remote/company
MySQL targets without sending company credentials to the public web API. It
runs on the user's machine; the browser talks to it directly.

## Security boundary

- Listens on `127.0.0.1:8765` only: no `0.0.0.0`, wildcard or IPv6 listener.
- Accepts requests only from an explicit allowlist of browser origins.
- A browser gets a session only by entering a single-use pairing code printed
  in the launcher terminal. Sessions live in memory.
- Unknown routes return `404`. Browser sessions are limited to a small route
  allowlist (see [Session scopes](#session-scopes)).
- Outbound database connections go only to approved targets. A target is
  approved either with the console commands or from the page: the page can only
  *ask* for a target, and approval needs the one-time code that the console shows
  next to the exact request (see [Adding a target from the page](#adding-a-target-from-the-page)).
  For every operation the browser refers to a target by its `target_id`; it
  cannot supply a hostname, IP, port, TLS setting or database target of its own.
- Every company connection re-checks the approved DNS identity and the exact
  destination IP, and requires TLS verified against the target's trust source.
  If that trust source is missing or unusable, the operation fails closed before
  any TCP connection is opened.
- No generic SQL endpoint: discovery is a fixed, capped `SHOW DATABASES`, and
  evidence is limited to `EXPLAIN` of an eligible submitted `SELECT`, as
  regenerated by the parser (never its execution), and fixed metadata queries.
  An eligible `SELECT` calls only names on the reviewed list of MySQL built-ins
  (see SECURITY.md); anything else gets no plan request. Every company
  evidence connection is set to read-only transactions and MySQL must confirm
  it before any evidence query; otherwise the connection is closed and the
  request fails with `database_connection_failed`. It is read back again
  before each plan request; if it is no longer confirmed, nothing is sent, the
  connection is closed and the remaining statements get no evidence. `UPDATE`/`DELETE`
  plans are never requested (`plan_not_collected_read_only`), so the company
  login needs no write privilege. The operator-only `/explain` route runs a
  bounded `EXPLAIN SELECT` built from validated identifiers and refuses
  `EXPLAIN_UPDATE`/`EXPLAIN_DELETE` with `plan_not_collected_read_only`.
- Company MySQL credentials are supplied per request and never stored (see
  [Company MySQL credentials](#company-mysql-credentials-per-request-never-stored)).

### Localhost connection test (`/db/test`)

A localhost-only MySQL connection test route exists but is **disabled by
default**. It is enabled only in a runtime created explicitly with
`create_stage2_app()`; the launcher does not enable it. When enabled it accepts
only `localhost`/`127.0.0.1` on port `3306`, requires a valid session and
origin, uses the supplied credentials for that one attempt, never logs, stores
or returns them, and closes the connection immediately.

## Running locally

```powershell
python -m connector --allow-origin http://localhost:8420
```

The launcher (`connector/launcher.py`) binds to `127.0.0.1:8765`, prints a
single-use pairing code (5 minute lifetime; press Enter for a new one) and serves
`create_app()`. Pairing codes are only ever issued in-process and printed to the
terminal; no HTTP route issues them, and they are never logged.

## Configuration

- Allowed browser origins: `--allow-origin ORIGIN` (repeatable) or the
  `CONNECTOR_ALLOWED_ORIGINS` environment variable (comma-separated). There is no
  default; with none configured the launcher refuses to start and a bare
  `create_app()` rejects every origin. Origins are normalised to
  `scheme://host[:port]`; wildcards, `null`, paths, credentials and non-loopback
  `http` origins are rejected.
- Browser session lifetime: `--session-ttl SECONDS` (60 to 28800, default 3600).
- Target registry file: `--registry PATH`, else `CONNECTOR_TARGET_REGISTRY`, else
  `connector-targets.json` in the per-user data folder:
  - Windows: `%LOCALAPPDATA%\MySQLDBAValidator\`
  - macOS and Linux: `$XDG_STATE_HOME/MySQLDBAValidator/` if `XDG_STATE_HOME` is
    set, else `~/.local/state/MySQLDBAValidator/`

  The resolved path is shown at startup. A registry that exists but cannot be
  loaded stops the launcher (exit code 2) and is left untouched.
- Company TLS CA: `--tls-ca PATH` or `CONNECTOR_TLS_CA` (PEM bundle containing at
  least one CA certificate), used by targets whose trust is `configured` (all
  targets approved with the console commands). An invalid bundle stops the
  launcher. With none configured the connector still starts, but those targets
  fail closed before any TCP connection is opened. Targets added from the page
  can use an uploaded CA bundle or (on Windows only) the Windows certificate
  store instead.
  Client certificates are not configurable from the launcher.

```powershell
python -m connector --allow-origin http://localhost:8420 `
  --registry D:\connector\targets.json --tls-ca D:\connector\company-ca.pem
```

### Reusing the configuration

Every connector setting is non-secret, so it can be saved for repeated use:

- From a source checkout: save the launch command above in a script, or set
  `CONNECTOR_ALLOWED_ORIGINS`, `CONNECTOR_TARGET_REGISTRY` and
  `CONNECTOR_TLS_CA` as user environment variables. A flag overrides its
  environment variable.
- Packaged app: the launcher loads `.env` from the data folder above
  (`%LOCALAPPDATA%\MySQLDBAValidator\.env` on Windows,
  `~/.local/state/MySQLDBAValidator/.env` on macOS unless `XDG_STATE_HOME` is
  set; `--registry` and `CONNECTOR_TARGET_REGISTRY` do not move it) into its
  environment before it
  starts the connector, so `CONNECTOR_TLS_CA=` and `CONNECTOR_TARGET_REGISTRY=`
  lines there apply on every start. The console app also accepts `--tls-ca`,
  `--registry` and `--session-ttl`.
- The session lifetime has no environment variable: pass `--session-ttl`.
  Choose it to fit your organisation's policy on idle and unattended
  workstations; the default stays 3600 seconds.

Never put company MySQL usernames or passwords in `.env` files, launch
scripts, environment variables or the target registry. The page asks for the
login on each operation, and the connector never reads company credentials from
configuration.

## Network, DNS and TLS prerequisites

- **Routing is the operator's job.** The connector opens a plain TCP connection
  from this machine to the approved host and port, so VPN, LAN, routing and
  firewall rules must already allow it. There is no proxy or SSH-tunnel
  support, and loopback, link-local, multicast, unspecified and reserved
  addresses are refused, so a local port forward cannot be used as a target.
- **DNS pinning.** Approval records the addresses the host name resolves to.
  Every connection resolves it again and must get exactly that set, or it fails
  with `dns_identity_mismatch`. Approve a target on the same network path the
  DBAs use (split-horizon DNS can answer differently off the VPN). When
  addresses change legitimately (failover, load balancing), someone at the
  console reviews the new addresses and approves again: **Request re-approval**
  in the page, or `approve <id>` in the console. The connector never refreshes
  approved addresses by itself.
- **TLS is mandatory.** Each target has one trust source (below). The connector
  connects to the approved IP but verifies the certificate chain against that
  trust source and the certificate against the approved host name; there is no
  option to disable either check and no plaintext fallback. A server that does
  not offer TLS is refused before the login is sent. The connector builds the
  `ssl.SSLContext` itself and passes it to PyMySQL (its supported API), and
  refuses any connection PyMySQL would not run in TLS-required mode. Python's
  `VERIFY_X509_STRICT` flag stays off, as PyMySQL had it; chain and host-name
  verification still apply. Turning it on is a separate decision that needs
  evidence from real server certificate chains.

## Connection errors

Company connection failures return a stable code and never the driver's
message, host, IP address, username or certificate details. Discovery and
validation return the same codes (validation with HTTP 400, discovery with HTTP
500, as before); a database failure never ends the connector session (never
401/403). Nothing is retried automatically: repeated failed logins can lock the
account (`FAILED_LOGIN_ATTEMPTS`) or block this machine (`max_connect_errors`).

| Code | Meaning (MySQL error) |
| --- | --- |
| `tls_verification_failed` | Server certificate not valid for the CA bundle or host name |
| `tls_handshake_failed` | Another TLS handshake failure |
| `tls_not_offered` | The server offered no TLS; the login was not sent (2026) |
| `auth_failed` | Login rejected (1045); MySQL does not say whether the user exists |
| `password_expired` | Expired password (1862, 1820) |
| `account_locked` | Locked by an administrator (3118) or after failed logins (3955) |
| `host_not_allowed` | Account may not connect from this host (1130) |
| `host_blocked` | Host blocked after repeated connection errors (1129) |
| `auth_method_unsupported` | Authentication method the driver cannot use (1251, 2059) |
| `connection_limit_reached` | Server or account connection/resource limit (1040, 1203, 1226) |
| `network_timeout` | TCP connect or handshake timed out |
| `connection_refused` | The connection to the approved port was refused |
| `unreachable` | Other network failure or lost connection (2003, 2006, 2013) |
| `dns_resolution_failed`, `dns_result_invalid`, `unsafe_destination`, `dns_identity_mismatch`, `target_needs_reapproval`, `target_not_approved` | Destination checks, before any connection |
| `database_connection_failed` | Anything else, including a session MySQL did not confirm as read-only or a trust source that is missing or changed (discovery reports `database_discovery_failed`) |

## Adding a target from the page

The DBA can add a target without typing console commands, but approval still
needs someone at the connector console.

1. Pair the page. Under **Add a remote connection**, enter a name, host name and
   port, and choose how the server certificate is trusted.
2. **Request approval** sends `POST /company/target-requests` with those details
   only (unknown fields, including any MySQL login, are rejected). The connector
   validates the host name, resolves it, refuses unsafe addresses, and prints a
   block in its console: name, host, port, every resolved address, the trust
   choice (for a CA bundle, its SHA-256 and certificate subjects) and an
   approval code `XXXX-XXXX`. No connection to the target is made.
3. If every line is what was asked for, the DBA enters the code in the page;
   `POST /company/target-requests/confirm` sends it in the request body. The
   connector checks that the request belongs to the same session, is unexpired
   and unused, and that the host still resolves to exactly the addresses shown,
   then writes the CA bundle (if any) and registers and approves the target in
   one registry write.
4. The DBA enters their MySQL login and uses **Discover databases** to test the
   connection (TLS, login, read-only confirmation). Approved targets appear in
   the Target list in later sessions; the login is never kept.

Request rules:

- A request expires after 300 seconds and its code works once. Three wrong
  codes cancel it. Five failed confirmations in 60 seconds pause confirmations
  for a minute (separately from pairing). Each session has at most one open
  request (a new one replaces it), and at most three are open overall. Requests
  are kept in memory only and end on unpair, session expiry or connector stop.
- Requests are accepted only when the connector runs in an interactive terminal
  (`MySQL-DBA-Validator Console.exe` on Windows, `MySQL-DBA-Validator Console`
  started from Terminal on macOS, or `python -m connector`); otherwise
  `approval_console_unavailable`. The HTTP access log is off so request lines
  never mix with approval blocks. Codes and session tokens are never in URLs
  or logs.
- Host names must be ASCII DNS names: letters, digits, `-` and `_`, labels of 1
  to 63 characters, at most 253 characters, no trailing dot, and a last label
  that starts with a letter (so `10.1` or `2130706433` are refused). Names in
  other scripts are entered in their `xn--` form. Host names from the page are
  stored in lower case. IP literals are not accepted.
- Display names from the page are 1 to 64 characters with no control or format
  characters. Every value the console prints (including the `targets` listing)
  is escaped, so text cannot add lines or terminal escape sequences.
- The code proves that someone who could see this console relayed it to the
  same paired session within five minutes. It does not prove they read the
  block, so check it before entering the code.

Trust sources (stored per target in the registry's `tls_policy`):

| Choice | Policy | Verified against |
| --- | --- | --- |
| Connector CA bundle | `configured` (also existing targets with no policy) | `--tls-ca` / `CONNECTOR_TLS_CA` |
| CA bundle file | `bundle:<sha256>` | The uploaded PEM bundle, stored as `<sha256>.pem` in a `trust` folder next to the registry |
| Windows certificate store | `system` | The Windows `CA` and `ROOT` stores (Windows only; refused elsewhere) |

A CA bundle must be ASCII PEM `CERTIFICATE` blocks only, at most 256 KiB, with
at least one CA certificate; anything containing a private key is refused. A
binary (DER) certificate, often named `.cer` or `.crt`, is refused too, and
renaming it does not convert it: export it again in PEM (Base-64) form. The
file is written before the registry refers to it, and its SHA-256 is checked on
every connection with exactly the bytes then loaded. A missing, changed or
unreadable bundle, an empty certificate store, a missing `--tls-ca` for a
`configured` target, or an unknown policy fails that target closed. The
connector never falls back to another trust source. Older versions ignore
`tls_policy` and use `--tls-ca`, which verifies or fails closed.

Re-approval (**Request re-approval**, offered after `dns_identity_mismatch` or
`target_needs_reapproval`) uses the same code flow for an existing target. It
cannot change the host, port or trust, and it shows the old and new address
sets. Revoked targets can only be re-approved in the console.

Not supported: IP-literal endpoints, SSH tunnels, local port forwards, proxies
or cloud connectors (loopback is refused), vendor IAM or other token logins,
and client-certificate authentication. Network access (VPN, routing, private
DNS, firewalls, security groups) and any CA bundle not covered by the chosen
trust source are the user's or administrator's responsibility.

## Operator console (target lifecycle)

Targets can also be managed by typing commands in the launcher terminal. Whoever
can see or type there is the operator: the same trust model as the pairing and
approval codes printed there. No command takes MySQL credentials. (The console
starts only when stdin is an interactive terminal.)

```text
targets                               list all targets and their states
register <id> <host> <port> <name...> register a target (always pending)
approve <id>                          snapshot the host's DNS identity and approve
reapprove <id>                        explicit re-approval of a needs_reapproval target
revoke <id>                           stop use until approved again
delete <id>                           remove; the id can never be reused
help
```

Each command prints one line with the outcome or a stable error code, and is
persisted atomically before it reports success. Approve, reapprove, revoke and
delete invalidate every session's discovered database list for that target.

## Company MySQL credentials (per request, never stored)

The browser supplies company MySQL credentials to the local connector per
operation. The connector uses them for that operation and does not persist them.

- Remote validate, database discovery, connect and explain each take `username`
  and `password` in the JSON request body (never in URLs or query strings).
- The connector is not a credential vault: there is no credential-provisioning
  endpoint, no Windows Credential Manager integration, and no code path that
  stores, reads back, or deletes a user's MySQL credentials.
- Credentials are never written to the target registry, session state, logs,
  error messages or responses, and never reach the public FastAPI API.
- Python cannot guarantee that memory is wiped; "per request" means the
  credentials exist only in the request/operation scope that needs them.
- Target approval is persistent; user MySQL credentials are not. The target
  registry and user credentials are separate concepts.
- Discovered database lists are stored per (target, browser session) and bound
  to a keyed fingerprint of the MySQL username, so another login, session or
  target cannot reuse them, and sessions never overwrite each other's lists. A
  session's lists are dropped on unpair or expiry. This binding is not
  authorization: every operation still requires a valid session, an approved
  target, destination validation, and MySQL accepting the supplied login.

Remote validate collects evidence on the per-request connection, which returns
dictionary rows (the same row contract as local validation), and scores it with
the same shared pipeline as local `/api/validate` (EXPLAIN adjustments, then
metadata M1 and M2). Metadata is only collected for the selected, discovered
database; without one it is reported unavailable rather than read from local
`.env` settings. A collector failure leaves the static result usable.

Request-size limits: remote validate accepts bodies up to 128 KiB with SQL up to
64 KiB of UTF-8 (the same SQL limit as the public API); every other connector
route keeps the 4 KiB limit. Limits are enforced with or without a
`Content-Length` header.

## Target registry

Approved targets persist in a versioned JSON file (`--registry` /
`CONNECTOR_TARGET_REGISTRY` / per-user default, see Configuration).
Writes are atomic (temp file, fsync, replace). A registry that cannot be parsed or
fails validation is never replaced; loading fails closed with a clear error. The
file holds destination policy only and rejects unknown fields.

Loading applies the current host-name rules (see
[Adding a target from the page](#adding-a-target-from-the-page)). A target saved
earlier whose host name they now refuse (for example a non-ASCII name, a
numeric last label such as `db.10`, or more than 253 characters) stops the
connector from starting (exit code 2); the error names the entry, for example
`invalid_target:targets[2]` (counting from 0). The registry is not rewritten or
repaired automatically, and there is no migration. Keep a copy of the file and
its `trust` folder, remove only that entry, start the connector, and add the
target again with a host name the current rules accept, so that it is approved
again: the `xn--` form of a non-ASCII name, or, when the old name has no valid
form (such as `db.1corp`), another DNS name or alias that resolves to the same
server, if your DNS provides one. Editing the host
name in place does not work: the entry's DNS snapshot and TLS host name must
match it.

## Session scopes

- Browser sessions last a fixed time from pairing (`--session-ttl`); nothing
  extends them. The page warns before expiry and, once the session ends, asks
  for a new pairing code. After re-pairing it reselects the previous target
  only if the new session still lists it as approved; the MySQL login is never
  kept and databases must be discovered again. Unpair, or choosing Local,
  forgets the target.
- `browser` sessions (from launcher pairing codes) may only call `GET /health`,
  `POST /unpair`, `GET /company/targets` (approved targets only),
  `POST /company/targets/{id}/databases` and `/validate`, and
  `POST /company/target-requests` and `/company/target-requests/confirm` (a
  request is approved only with the console code). Every other route returns
  `403 insufficient_session_scope`. The approved-target, DNS, TLS and
  exact-destination checks still apply.
- `operator` sessions keep the full HTTP capability (target registration,
  approval, revocation, deletion, discovery, connect, bounded `/explain`). The
  former signed `/evidence` route has been removed; remote evidence comes from
  `/validate`. Operator sessions are only issued
  programmatically (`ConnectorRuntime.issue_pairing_token()`). The production
  operator workflow is the launcher's operator console, which needs no session.
